# 09. Проектная часть пояснительной записки

В данном разделе представлена проектная часть курсового проекта **«Street Retail Aggregator»** — корпоративной информационной системы (КИС) для поиска, аренды и сдачи коммерческой недвижимости формата «стрит-ритейл» с интеллектуальной рекомендательной системой на основе геоданных. Раздел разбит на три ключевых подраздела, содержащих исчерпывающее обоснование архитектурных, технологических и даталогических решений.

---

## 1. Выбор и обоснование программно-аппаратного обеспечения

### 1.1. Критерии отбора программно-аппаратного обеспечения
Отбор программных и аппаратных компонентов системы производился исходя из специфики объекта и предмета исследования:
*   **Объект исследования:** Рынок коммерческой недвижимости стрит-ритейла, процессы публикации объявлений, фильтрации и подбора торговых площадей для малого/среднего бизнеса.
*   **Предмет исследования:** Системы пространственного анализа (ГИС), скоринговые алгоритмы оценки конкуренции и синергии, кроссплатформенные технологии разработки ГИС-ориентированных приложений.

На основе этого были сформулированы следующие **критерии отбора программно-аппаратного обеспечения**:
1.  **Кроссплатформенность клиентской части:** Обеспечение работоспособности на мобильных устройствах (Android, iOS) для предпринимателей «в поле» и на персональных компьютерах (Web/Desktop) для офисной работы арендодателей.
2.  **Скорость ГИС-вычислений и автономность:** Скоринг помещений (вычисление плотности конкурентов и синергичных соседей вокруг координат) должен занимать не более 500 мс. Это исключает прямую зависимость от медленных и лимитированных публичных гео-сервисов (Google Places, Yandex Maps API с их жесткими лимитами запросов). Требуется возможность развертывания локального ГИС-сервера.
3.  **Многопоточность бэкенда:** Поддержка параллельных вычислений при пакетном скоринге (одновременный расчет рейтинга для 20–30 объектов на карте).
4.  **Безопасность и соответствие законодательству РФ:** Возможность шифрования данных, разграничения доступа по ролям (RBAC) и развертывания СУБД на российских серверах для соблюдения требований ФЗ-152 «О персональных данных».
5.  **Лицензионная чистота и стоимость:** Приоритет отдается бесплатному программному обеспечению с открытым исходным кодом (Open Source), не требующему покупки коммерческих лицензий.

### 1.2. Критерии оценки для сравнительного анализа альтернатив
Для проведения сравнительного анализа альтернативных технологий были выделены 7 критериев оценки. Каждый критерий оценивается по шкале от 1 до 5 баллов:
*   **К1: Производительность и время отклика** (эффективность многопоточности, работа с памятью, время инициализации).
*   **К2: Скорость разработки и зрелость экосистемы** (наличие готовых библиотек, качество документации, обилие готовых решений).
*   **К3: Стоимость владения и лицензии** (5 — полностью бесплатное ПО с лицензией MIT/Apache/BSD, 1 — проприетарное дорогостоящее ПО).
*   **К4: Кроссплатформенность среды** (возможность компиляции под разные ОС из единого исходного кода).
*   **К5: Поддержка пространственных (ГИС) запросов и гео-индексации** (наличие готовых типов данных Point/Polygon, пространственных индексов R-Tree/GiST).
*   **К6: Надежность и транзакционность (ACID)** (гарантии ссылочной целостности, защита от сбоев).
*   **К7: Локальность развертывания (оффлайн-режим)** (возможность полноценного запуска всех модулей на собственном сервере без внешних API).

#### Обоснование выбора стека технологий:
1.  **Backend: Spring Boot 3 + Java 21.** Набрал максимальные баллы благодаря зрелой многопоточности (ForkJoinPool в Java используется бэкендом для параллельной оценки списка недвижимости), встроенным механизмам безопасности (Spring Security, JWT) и строго типизированной архитектуре. В отличие от Python/Django, Java демонстрирует более высокую производительность при расчете тяжелых алгоритмов скоринга.
2.  **Frontend: Flutter (Dart).** Позволяет создать кроссплатформенное приложение с компиляцией в нативный код (AOT). Это гарантирует плавный UX карты (MapLibre/OSM tiles) с частотой 60 FPS, что сложно реализовать на React Native с его JS-мостом.
3.  **СУБД: PostgreSQL 16.** Является стандартом де-факто для ГИС-ориентированных реляционных КИС. Поддерживает сложные ACID транзакции, JSON-колонки (для L2-кэша ГИС-ответов) и обладает мощным расширением PostGIS для будущих пространственных индексов. MongoDB отклонена из-за слабой поддержки ACID и транзакционных связей.
4.  **ГИС-движок: Локальный Overpass API (`wiktorn/overpass-api` в Docker).** Решает ключевую проблему проекта — скорость отклика. Локальный контейнер с базой данных Центрального федерального округа РФ (около 40 ГБ в индексе) обрабатывает тяжелые QL-запросы пространственного поиска конкурентов за **10–100 мс** против **10–60 с** у публичных зеркал. Внешние Yandex и Google API отклонены из-за высокой стоимости лицензий для коммерческого использования и невозможности оффлайн-развертывания.

## 2. Критерии отбора и характеристика используемых данных

### 2.1. Критерии отбора данных
Для реализации алгоритма скоринга и визуализации объектов недвижимости на карте были определены следующие требования к данным:
1.  **Наличие точной геопривязки:** Любой объект (помещение или торговая точка конкурента) должен обладать географическими координатами в проекции WGS 84 (широта и долгота с точностью не менее 6 знаков после запятой).
2.  **Технические характеристики помещений:** Обязательное присутствие параметров: площадь (м²), цена (₽/мес), электрическая мощность (кВт), наличие мокрых точек (водоснабжения), вентиляционной вытяжки, отдельного входа с улицы, этажа и высоты потолков.
3.  **Инфраструктурный контекст (POI):** Данные об окружающих бизнесах должны быть классифицированы по категориям (аптеки, кофейни, ПВЗ и т.д.) с привязкой к тегам OpenStreetMap для однозначного определения прямых конкурентов и синергичных соседей.
4.  **Транспортная доступность:** Данные о станциях метро, входах в метрополитен и остановках общественного транспорта с указанием типа транспорта.

### 2.2. Характеристика отобранных данных и источники
В системе используются два принципиально разных источника данных:

#### А. Пространственные данные OpenStreetMap (OSM)
*   **Источник:** Географическая база данных OpenStreetMap. Срез данных загружается в формате `.osm.pbf` с зеркала Geofabrik (файл Центрального федерального округа РФ, объем ~600 МБ в сжатом виде, разворачивается в ~40 ГБ базы данных ГИС).
*   **Характеристика:** Включает в себя узлы (`Node`), пути (`Way`) и отношения (`Relation`). Каждый географический объект имеет набор тегов (пар `ключ=значение`).
*   **Программа генерации/обработки:** Локальный ГИС-сервер Overpass API в Docker. Для конвертации PBF-файлов используется утилита `osmium` внутри контейнера.

## 3. Регламент хранения и обработки персональных данных (ФЗ-152)

Поскольку информационная система «Street Retail Aggregator» собирает, обрабатывает и хранит данные физических лиц (включая индивидуальных предпринимателей и представителей юридических лиц), на нее в полной мере распространяется действие Федерального закона РФ **ФЗ-152 «О персональных данных»**.

### 3.1. Перечень обрабатываемых персональных данных
В СУБД PostgreSQL системы хранятся следующие персональные данные (ПДн):
1.  Адрес электронной почты (`users.email`) — используется как логин.
2.  Хэш пароля (`users.password_hash`).
3.  Фамилия, имя, отчество пользователя (`tenant_profiles.name` или `landlord_profiles.company_name`).
4.  Номер мобильного телефона (`tenant_profiles.phone`, `landlord_profiles.phone`, `properties.contact_phone`).
5.  Индивидуальный номер налогоплательщика (`tenant_profiles.inn`, `landlord_profiles.inn`) — относится к ПДн физических лиц и ИП.
6.  Аватары пользователей (`users.avatar_url`).
7.  История откликов на объявления и лог просмотров недвижимости.

---

### 3.2. Регламент и технические меры по защите ПДн
Для обеспечения соответствия законодательству РФ внедрен следующий регламент:

1.  **Правовое основание обработки (Согласие):**
    *   При регистрации в приложении Flutter пользователь обязан явно выразить согласие с Политикой конфиденциальности и дать согласие на обработку персональных данных (установкой чекбокса). Без согласия регистрация блокируется.
2.  **Локализация баз данных (ст. 18.1 ФЗ-152):**
    *   База данных PostgreSQL и файловый сервер хранения аватаров/фотографий недвижимости развернуты на хостинге, физически расположенном в дата-центре на территории Российской Федерации.
3.  **Криптографическая защита паролей:**
    *   Пароли пользователей никогда не хранятся в открытом виде. Бэкенд на уровне `ApplicationConfig` настраивает `BCryptPasswordEncoder` (cost factor = 10). Пароль хэшируется с солью перед сохранением в колонку `users.password_hash`. Дехэширование технически невозможно.
4.  **Защита каналов связи (Шифрование при передаче):**
    *   Обмен данными между мобильным приложением Flutter и REST API Spring Boot защищен протоколом HTTPS. Безопасный TLS-туннель организуется с помощью сервиса Cloudflare Tunnel (`cloudflared`), который проксирует внешний защищенный адрес на локальный порт бэкенда (`localhost:8080`).
5.  **Минимизация данных в сессиях (Stateless-архитектура):**
    *   В системе отсутствуют классические серверные сессии и сессионные cookies. Доступ предоставляется по технологии JWT (JSON Web Token).
    *   Время жизни токена ограничено 24 часами. Токен содержит только email (`sub`) в качестве payload. Роли, права и ID пользователя извлекаются из СУБД на каждый запрос, что предотвращает утечку полномочий в JWT.
6.  **Разграничение прав доступа (Role-Based Access Control):**
    *   Все контроллеры бэкенда защищены фильтром `JwtAuthenticationFilter`. Права доступа проверяются через Spring Security. Публичными являются только эндпоинты авторизации и просмотра карточки недвижимости без личных данных арендодателя.
7.  **Реализация права на забвение:**
    *   Арендатор имеет техническую возможность удалить историю своих заявок (реализовано свайпом во Flutter-приложении с вызовом `DELETE /api/applications/{id}`). При удалении аккаунта каскадно (`CascadeType.ALL` на связи в JPA) уничтожаются профили (`TenantProfile`/`LandlordProfile`), файлы аватаров и связанные записи, исключая остаточное хранение ПДн.

## 4. Ролевая модель пользователей

В системе «Street Retail Aggregator» реализована ролевая модель доступа на основе ролей (**RBAC**), разделяющая пользователей по типам их бизнес-активности.

### 4.1. Иерархия и матрица прав доступа
В системе выделены три роли: `TENANT` (Арендатор), `LANDLORD` (Арендодатель), `ADMIN` (Администратор).

| Функциональная возможность | Арендатор (TENANT) | Арендодатель (LANDLORD) | Администратор (ADMIN) |
|---|:---:|:---:|:---:|
| Регистрация, авторизация и верификация почты | Да | Да | Да |
| Создание поисковых профилей (`SearchProfile`) | Да | Нет | Нет |
| Поиск недвижимости на карте с расчетом скоринга | Да | Нет | Нет |
| Добавление недвижимости в избранное (`favorites`) | Да | Нет | Нет |
| Подача заявки на аренду (`Application`) | Да | Нет | Нет |
| Удаление истории своих заявок | Да | Нет | Нет |
| Просмотр входящих заявок от арендаторов | Нет | Да | Нет |
| Смена статусов заявок (`PENDING` -> `REVIEWING` -> `ACCEPTED`/`REJECTED`) | Нет | Да | Нет |
| Создание, редактирование, удаление помещений (`Property`) | Нет | Да | Нет |
| Просмотр дашборда аналитики просмотров и конверсий | Нет | Да | Нет |
| Чат реального времени (в рамках поданной заявки) | Да | Да | Нет |
| Верификация профиля арендодателя (`isVerified = true`) | Нет | Нет | Да |
| Управление справочником категорий бизнеса | Нет | Нет | Да |

### 4.2. Правила назначения и верификации пользователей
1.  **Выбор роли при регистрации:** Роль жестко указывается пользователем в момент отправки формы регистрации (`RegisterRequest.role`). После успешного создания изменить роль для данной учетной записи невозможно.
2.  **Двухэтапная верификация учетной записи (Email Verification):**
    *   При регистрации бэкенд создает запись в таблице `users` со статусом `UserStatus.UNVERIFIED`. Доступ к защищенным эндпоинтам API для такой записи заблокирован.
    *   Генерируется случайный 6-значный цифровой код, который записывается в БД (`users.verification_code`) со сроком жизни 2 минуты (`users.code_expires_at`).
    *   `EmailService` отправляет письмо с кодом на указанную почту через SMTP-сервер Google (порт 587, STARTTLS).
    *   Пользователь вводит код в приложении, отправляя запрос на `/api/auth/verify`. В случае совпадения кодов и соблюдения TTL статус пользователя меняется на `ACTIVE`, код из БД зануляется, и выдается JWT-токен для работы.
    *   **Защита от спама (Антифлуд):** Запросить повторную отправку кода (`/api/auth/resend-code`) можно только после истечения срока жизни предыдущего кода (не чаще, чем раз в 2 минуты).
3.  **Уникальность идентификаторов:** На уровне СУБД накладывается ограничение уникальности `UNIQUE` на `users.email` и `tenant_profiles.inn`. Внутри `AuthService` реализована проверка уникальности ИНН для арендодателей.
4.  **Административная верификация арендодателей:**
    *   Для исключения мошенничества арендодатель при регистрации указывает ИНН и название компании, получая профиль с флагом `isVerified = false`.
    *   Администратор системы через панель управления сверяет указанные ИНН/ОГРН по базам ФНС/ЕГРЮЛ и выставляет флаг `isVerified = true`, что повышает доверие к объявлениям арендодателя на карте.

## 5. Даталогическая модель хранения данных (в нотации Мартина)

Даталогическая модель системы спроектирована на основе реляционной парадигмы и полностью нормализована до **третьей нормальной формы (3NF)**.

### 5.1. Обоснование нормализации до 3NF
*   **Первая нормальная форма (1NF):** Все атрибуты всех таблиц являются атомарными. Списки (например, массив путей к изображениям недвижимости или тегов ГИС) вынесены в отдельные связанные таблицы (`property_images`, `property_existing_neighbors`).
*   **Вторая нормальная форма (2NF):** Схема находится в 1NF, и все неключевые атрибуты полностью функционально зависят от простых первичных ключей. Таблицы профилей `tenant_profiles` и `landlord_profiles` используют паттерн *Shared Primary Key* (`@MapsId` в JPA), где первичный ключ `user_id` является внешним ключом к таблице `users`, исключая частичные зависимости.
*   **Третья нормальная форма (3NF):** Схема находится во 2NF, и в ней отсутствуют транзитивные зависимости неключевых полей от первичного ключа. Данные о категориях бизнеса вынесены в отдельный справочник `business_categories`. В таблице `properties` хранится только внешний ключ `landlord_id` (ссылка на `users`), а не ФИО арендодателя или его телефон, что исключает избыточность и аномалии обновления.

## 6. Модель программно-аппаратного комплекса

Функционирование агрегатора коммерческой недвижимости «Street Retail Aggregator» обеспечивается специализированным программно-аппаратным комплексом (ПАК), реализующим трехзвенную клиент-серверную архитектуру.

### 6.1. Архитектурная схема взаимодействия ПАК
Взаимодействие компонентов ПАК организовано по следующей логической цепочке:

```
┌─────────────────────────────────────────────────────────────┐
│                 КЛИЕНТСКИЙ УРОВЕНЬ (Hardware)                │
│ Мобильные устройства (Android/iOS) и Персональные компьютеры │
└──────────────────────────────┬──────────────────────────────┘
                               │ HTTPS / TLS (Туннелирование)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                 СЕТЕВОЙ ТРАНСПОРТНЫЙ УРОВЕНЬ                 │
│         Cloudflare Tunnel (Сервис шифрования трафика)       │
└──────────────────────────────┬──────────────────────────────┘
                               │ localhost:8080 (Cleartext)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                  УРОВЕНЬ ПРИЛОЖЕНИЙ (Software)               │
│ Бэкенд-сервер Spring Boot 3 (Сервисы, Скоринг, WebSockets)  │
└──────┬───────────────────────┬──────────────────────────────┘
       │ TCP/IP                │ HTTP/2 (10-500ms)
       ▼                       ▼
┌──────────────┐       ┌──────────────────────────────────────┐
│  СУБД        │       │             ГИС-СЕРВЕР               │
│  PostgreSQL  │       │ Локальный контейнер Overpass API     │
│  (Хранилище) │       │ (База данных OSM ЦФО, Объем ~40 ГБ)  │
└──────────────┘       └──────────────────────────────────────┘
```

---

### 6.2. Функциональные возможности программно-аппаратного комплекса
1.  **Интерактивное картографирование:** Рендеринг векторных/растровых тайлов карты OpenStreetMap на клиенте Flutter с позиционированием объектов стрит-ритейла.
2.  **Интеллектуальный пространственный скоринг:**
    *   *Финансовый блок:* Оценка отклонения цены и площади объекта от параметров в `SearchProfile` арендатора.
    *   *Технический блок:* Жесткая проверка совпадения физических характеристик помещения (мощность кВт, вытяжка, вода, санузел, отдельный вход) с техническими требованиями арендатора.
    *   *Географический блок (Конкуренция и Синергия):* Бэкенд отправляет QL-запрос в локальный Overpass API, строит тепловую карту POI в заданном радиусе (до 5 км), выявляет прямых конкурентов (по тегам OSM) и снижает балл при их наличии; находит синергичные точки (университеты, БЦ, остановки метро для общепита) и начисляет бонусные баллы.
    *   *Транспортный блок:* Оценка пешеходной доступности до станций метро и остановок.
3.  **Коммуникационная WebSocket-подсистема:** Реал-тайм доставка сообщений чата между арендатором и арендодателем в рамках отклика на аренду по протоколу STOMP поверх WebSockets (с автоматическим SockJS fallback для браузеров).
4.  **Аналитический дашборд:** Подсчет просмотров помещений, фактов добавления в избранное и конверсии в заявки по дням и неделям (с дедупликацией просмотров по авторизованным пользователям).
5.  **Интеграция с искусственным интеллектом (LLM):** Автоматическая генерация текстового объяснения итоговой оценки помещения на естественном языке с помощью API OpenRouter (модели Llama 3.3 / Qwen / GLM-4.5) на основе детального JSON-расклада скоринга.

### 6.3. Минимальные технические требования

#### А. Серверная часть (аппаратные ресурсы для развертывания бэкенда, СУБД и ГИС)
Для развертывания ПАК в тестовом режиме на одном физическом или виртуальном хосте (Single-Host Development/Production) предъявляются следующие минимальные требования:

*   **Процессор (CPU):** Архитектура x86-64, не менее 4 физических ядер с тактовой частотой от 2.5 ГГц (высокая производительность на одно ядро критична для компиляции OSM-данных движком Overpass).
*   **Оперативная память (RAM):**
    *   *Минимум:* **16 ГБ** (4 ГБ — JVM бэкенда и СУБД PostgreSQL, 8 ГБ — кэш страниц диска и RAM-буферы диспетчера Overpass API, 4 ГБ — операционная система).
    *   *Рекомендуется:* **32 ГБ** (для стабильной работы Overpass при тяжелых параллельных запросах).
*   **Дисковая подсистема (Storage):** Накопитель **SSD (SATA/NVMe)**. Использование HDD категорически не допускается из-за огромного количества мелких случайных операций чтения (Random Read) при поиске POI вокруг координат.
    *   *Свободный объем:* Не менее **100 ГБ** (из которых ~40 ГБ занимает база данных OSM ЦФО, ~10 ГБ база данных PostgreSQL и логи, ~10 ГБ системные службы Docker и NSSM, остальное — резерв под медиа-файлы объявлений).
*   **Операционная система:**
    *   Windows 10/11 Professional / Windows Server 2019+ с установленным Docker Desktop и подсистемой WSL2.
    *   Или Linux (Ubuntu 22.04 LTS, Debian 12) с установленным Docker Engine и Docker Compose.
*   **Программное окружение на сервере:**
    *   Java Runtime Environment (JRE) / JDK 21 (например, Eclipse Adoptium OpenJDK).
    *   Docker Engine 20.10+.
    *   Утилита NSSM (Non-Sucking Service Manager) для инсталляции JAR бэкенда в качестве системного Windows-сервиса (в случае развертывания под ОС Windows).
*   **Сеть:** Выделенный статический IP-адрес или установленная служба Cloudflare Tunnel (`cloudflared`) для проксирования HTTPS-трафика. Скорость интернет-соединения от 50 Мбит/с.

#### Б. Клиентская часть (мобильное или десктопное устройство пользователя)
*   **Мобильные платформы:**
    *   *Android:* ОС Android 8.0 (API level 26) и выше, оперативная память от 2 ГБ, поддержка OpenGL ES 2.0 (необходима для рендеринга векторных карт).
    *   *iOS:* ОС iOS 13 и выше, iPhone 7 и новее.
*   **Персональные компьютеры (Web-интерфейс / Десктоп-версия):**
    *   Браузер с поддержкой WebGL (Google Chrome 90+, Mozilla Firefox 88+, Apple Safari 14+).
*   **Аппаратные датчики:** Наличие GPS/ГЛОНАСС модуля на мобильном устройстве для автоматического позиционирования пользователя на карте.
